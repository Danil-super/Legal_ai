# Личная помощь: закрытая разработка

Текущий клинический бот не изменён. Второй бот существует как отдельная точка
запуска, но не зарегистрирован и не запущен этим коммитом. В production Compose
нет нового сервиса; дополнительные секреты для текущего деплоя не нужны.

## M1 — технический прототип

- `legal_core.personal.contracts`: отдельная аудитория/владелец/пространство,
  типизированная хронология. Это не готовая авторизация или хранилище дел.
- `legal_core.personal.catalog`: шесть вымышленных ситуаций и примеры уточнений.
- `legal_core.personal.preview_api`: самостоятельная фабрика FastAPI, только чтение
  каталога и фиксированных примеров, никаких `/cases`, загрузок или LLM.
- `telegram_gateway.personal_preview`: отдельный второй бот, только кнопки примеров.

`PERSONAL_PREVIEW_MODE` по умолчанию `off`. Запуск второго модуля в этом режиме
завершается до создания бота; API в этом режиме регистрирует только liveness.
Ошибочные значения и `live` запрещены. Даже включённый `synthetic` не открывает
реальные кейсы, расчёты или юридические выводы.

## Закрытая техническая проверка — только после отдельного решения

В отдельной среде с установленными locked dependencies:

```bash
# По умолчанию: ничего не запускает и не подключается к Telegram.
python -m telegram_gateway.personal_preview
# Отдельная API-фабрика; не clinical main, не публичный интерфейс.
python -m uvicorn legal_core.personal.preview_api:create_app --factory --host 127.0.0.1 --port 8021 --no-access-log
```

Для `synthetic` нужны отдельный `PERSONAL_PREVIEW_API_KEY` (случайный секрет
32–128 символов A–Z/a–z/0–9/_/-), точный список `PERSONAL_PREVIEW_TESTER_IDS`
(не более 32 ID через запятую, без wildcard) и разрешение на закрытый запуск.
Только для второго бота дополнительно нужны `PERSONAL_TELEGRAM_BOT_TOKEN` и
`CLINIC_TELEGRAM_BOT_ID`, чтобы исключить запуск на существующем клиническом боте.
Не копируйте клинический `app.env` в личный сервис. Секреты в Git не записывать.
Этим коммитом эти параметры нигде на сервере не установлены.

API принимает только два чтения:
`GET /v1/personal-preview/catalog` и
`GET /v1/personal-preview/scenarios/{id-из-каталога}`.
Требуются независимый Authorization: Bearer и X-Personal-Preview-Tester из allowlist.
Заголовки/тело с clinic_id/ролью не дают прав. Это служебный preview, не клиентский
механизм входа; публичный identity resolver должен быть реализован отдельно.

В боте текст и файлы отклоняются: не скачиваются, не сохраняются, не отправляются
модели и не повторяются в ответах. Но пользовательский файл уже поступил Telegram,
если пользователь его сам прислал. Поэтому не распространяйте этот прототип как
безопасный кабинет для персональных/медицинских сведений.

## Нормативная база

`legal-source-register.v1.json` — стартовый перечень задач проверки, не ingestion
manifest и не набор одобренных норм. Семь записей содержат первоисточники,
реквизиты, наблюдения и явно незавершённый статус. Проверка от 24.09.2026 была
проверкой обнаружения/метаданных; часть прямых запросов к pravo.gov.ru недоступна.
Текст страницы Минздрава о 323-ФЗ: https://minzdrav.gov.ru/documents/7025 — прочитан,
но не принят как доказательство текущей консолидированной редакции.

Манифесты №736 и №659 уже есть в репозитории и обозначены REVIEW_REQUIRED.
Они не изменены, файлы заново здесь не скачивались, production approval не проверялся.
Перед применением нужны исходный артефакт/хэш, изменения/периоды действия,
проверенные фрагменты и ручное одобрение. Отсутствие ошибок CI этого не заменяет.
Для ОМС, представительства, процесса, ГК РФ и иных тем перечень расширяется при
проектировании соответствующих сценариев, а не считается автоматически полным.
