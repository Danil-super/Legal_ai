# Закрытый пилот: допуск и техническая проверка

Этот документ — операционный чек-лист, а не юридическое заключение и не разрешение на обработку
персональных данных. Доступ `FREE_PILOT` открывает только ограниченный доступ выбранной клинике;
он не включает Hermes, не утверждает правовой корпус и не разрешает отправлять сообщения пациентам.

## Граница первого пилота

До завершения всех обязательных согласований допускается только закрытая техническая проверка с
обезличенными синтетическими сценариями и тестовыми аккаунтами. Нельзя загружать в бот медкарты,
снимки, переписку или документы конкретного пациента. В базу документов допускаются только
обезличенные шаблоны и локальные регламенты клиники.

Даже после допуска к пилоту бот формирует внутреннюю карточку/черновик, а не автоматически
юридически значимый ответ пациенту. `HIGH` и `CRITICAL` остаются в изолированной очереди
эскалации юристу.

## Обязательные стоп-условия

| Блок | Кто принимает решение | Что должно быть подтверждено | Статус до подписи |
|---|---|---|---|
| Правовой корпус | Платформенный `LEGAL_EDITOR` / медицинский юрист | Конкретные official-artifact версии сверены и одобрены по [чек-листу корпуса](legal-review/initial-corpus-review.md). | Заблокировано |
| Risk-policy и эскалация | Владелец продукта и медицинский юрист | Утверждены пороги, сценарии, обязанности юриста, каналы и срок реакции для `HIGH`/`CRITICAL`. | Заблокировано |
| ПДн, врачебная тайна, провайдер LLM | Ответственный за ПДн/ИБ и владелец сервиса | Согласованы состав данных, локализация, срок хранения, удаление/отзыв, договор с провайдером, шифрование и доступы. | Заблокировано |
| Эксплуатация | Технический владелец | CI зелёный из чистого checkout, миграции, readiness, резервное копирование и восстановление проверены. | Требует проверки |
| Пилотная клиника | Владелец сервиса и клиника | Назначены владелец, администратор, юрист для эскалаций и только тестовые Telegram ID. | Требует назначения |

При невыполнении любого пункта не подключайте реальных пациентов и не включайте внешнего LLM.
Система должна оставаться в безопасном режиме: без юридических рекомендаций и без автоотправки.

## Технический preflight

Выполняет технический владелец в чистом checkout и с отдельными небоевыми секретами.

1. Установить зависимости строго из lock-файла и выполнить:

   ```bash
   python -m pytest
   python -m ruff check .
   python -m mypy services/legal_core/src services/gateway/telegram/src services/agent_orchestrator/src
   ```

2. Проверить конфигурацию, не раскрывая секреты в консоли и логах:

   ```bash
   docker compose config --quiet
   docker compose -f docker-compose.yml -f ops/hermes/docker-compose.hermes.yml --profile analysis config --quiet
   ```

3. На изолированном стенде применить миграции, запустить сервисы и убедиться, что `GET /health/live`
   отвечает `200`, а `GET /health/ready` возвращает `status: ready` с успешными проверками зависимостей.
   Используйте отдельные хранилище и базу для стенда.

4. Прогнать минимальный сквозной сценарий только на синтетических данных:

   - владелец выдаёт ограниченный `FREE_PILOT` тестовому Telegram ID;
   - администратор создаёт кейс без данных пациента и получает внутреннюю карточку;
   - для `HIGH`/`CRITICAL` создаётся эскалация, а не внешний ответ;
   - администратор загружает один обезличенный шаблон, одобряет его и видит его метаданные в отчёте;
   - администратор подтверждённо снимает шаблон с использования; следующий анализ не содержит его
     фрагментов, а история версии сохраняется;
   - повторная загрузка того же типа создаёт новую версию и после отдельного одобрения может
     участвовать в последующих анализах только для периода своего действия.

5. Выполнить резервное копирование PostgreSQL и проверку восстановления на отдельной базе.
   Зафиксировать время восстановления, версию миграций и результат проверки tenant-изоляции.

6. Проверить наблюдаемость: логи и audit trail содержат идентификаторы событий, версий и
   retrieval snapshot, но не raw-документы, медицинские сведения или секреты.

## Решение о допуске

Перед включением доступа технический владелец прикладывает ссылку на зелёный CI и результаты
пунктов 3–6. Затем решения фиксируются отдельно, с датой и ответственным:

- медицинский юрист / `LEGAL_EDITOR` — правовой корпус;
- владелец и медицинский юрист — risk-policy и порядок эскалаций;
- ответственный за ПДн/ИБ — обработка данных, хранение и LLM-провайдер;
- владелец сервиса — состав пилотных клиник и срок `FREE_PILOT`.

Без всех четырёх записей доступ остаётся только техническим синтетическим стендом.

## Остановка пилота

При инциденте или сомнении в корректности ответа владелец немедленно отзывает entitlement
пользователя/клиники, приостанавливает внешний провайдер и переводит кейсы в ручную проверку.
Не удаляйте историю документов или отчётов вручную: дальнейшее хранение, изъятие и удаление
выполняются только по утверждённой политике ПДн и аудита.
