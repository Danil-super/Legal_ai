# ADR 0086: актуальные Telegram-кнопки и восстановление V2-карточки

## Контекст и дата

2026-10-14. Проверка production-композиции PTB на 49882e5 воспроизвела
перехват файлов V2 библиотекой документов клиники, отправку сохранённой фабулы
после отзыва доступа, изменение другого черновика старой кнопкой и потерю
актуальной revision после сохранённого вложения с потерянным HTTP-ответом.
Существующие 164 focused tests проходили, но не проверяли эти переходы.
Материалы и описания во всех воспроизведениях фиксированные и синтетические.

## Решение и границы

- Обработчик библиотеки документов пропускает document update к ConversationHandler,
  если выбран V2-черновик на шаге MATERIALS. Остальные библиотечные загрузки
  сохраняют свой явный режим. Неподдерживаемое медиа на MATERIALS получает
  сообщение о допустимых форматах; оно не сохраняется.
- Перед выполнением обработчика, способного вывести сохранённые сведения,
  gateway читает выбранный черновик через существующий защищённый Core API.
  Это проверка действующего membership, подписки и конкретного ресурса.
  Отказ завершает локальный ввод до отправки фабулы. Новых ролей, разрешений,
  исключений tenant scope или изменений auth policy нет.
- Callback ACK отправляется перед protected read. Повторное обращение к тому же
  helper внутри обработки update не отправляет второй ACK. ContextVar держит
  одну запись только в области этого вызова и сбрасывается в finally, включая
  отказ доступа и исключение; глобального кеша пользователей/callback IDs нет.
  ACK не разрешает выдачу cached tenant content до успешной проверки Core.
- Кнопка V1/V2 действует только из последнего фактически отправленного сообщения
  с контролами. Его message_id хранится в локальном кеше и исключается из
  draftData. Формат callback не меняется; действующие ограничения 64 UTF-8 bytes
  сохраняются. Новое сообщение выбора, фабулы или валидации заменяет источник
  кнопок. Старое сообщение не переключает текущий ответ и не подтверждает
  другую карточку. После рестарта пользователь открывает server-owned черновик
  и получает новые контролы. Старые V1 callback формы сохраняют совместимость;
  их originating message проверяется тем же способом, без конверсии данных.
- Авторизованный V1/V2 snapshot проверяется по draft ID, версии, состоянию и
  revision. Если revision изменилась, gateway открывает сохранённый серверный
  шаг и не применяет прежний текст или callback к новой версии карточки.
- Неоднозначная загрузка/последующее обновление состояния восстанавливают
  revision и статус материалов из Core. Подтверждённый upload receipt позволяет
  сообщить, что материал сохранён; наблюдаемый тип источника остаётся в кеше
  для следующего guarded save. При потерянном upload receipt gateway не
  утверждает, что именно последний файл сохранён. Если серверный read также
  недоступен, пользователь получает указание восстановить черновик через меню;
  текст не обещает отсутствия файла. Автоматического повтора upload нет.
- MATERIALS text/document handlers также читают protected snapshot до parsing или
  Telegram download. После upload receipt выполняется ещё один protected read:
  новая revision из upload не разрешает PUT всего устаревшего draftData.
  Из последнего серверного snapshot меняются только attachment/source flags,
  secondary PUT использует его optimistic revision. Изменённые eventSummary и
  другие несвязанные факты не заменяются кешем; последующая гонка даёт conflict
  и возвращает актуальное состояние через существующее reconciliation.

Не меняются REST/schema, миграции, хранение исходных bytes, юридический evidence,
policy, approval, сроки хранения и запрет автоматического ответа пациенту.
Кодировка HTTP-имён файлов — отдельное изменение ADR 0085.

## Альтернативы и последствия

Nonce в каждом callback потребовал бы менять wire формы и все сохранённые
кнопки. Привязка к фактическому сообщению позволяет оставить существующие формы,
при этом неподтверждённая старая кнопка не получает исключения.

Новые вопросы требуют дополнительного read выбранного черновика. Этот запрос
нужен до вывода сохранённых данных; проверка только во время последующего PUT
не защищала read. Недоступный Core временно завершает локальный ввод, а
server-owned draft остаётся доступен для восстановления после возвращения сервиса.

## Проверка и ограничения

Test-only RED commit ce890355: 9 failed / 6 passed на production composition и
настоящем HTTP client с заменёнными транспортами. Отдельный контроль ASCII
upload, актуального выбора/снятия выбора, навигации start/cancel/menu/resume и
ошибочного текста отличает восстановление от безусловного запрета действий.
Добавлены проверки изменённой серверной revision, secondary PUT до/после commit,
некорректного revision response и рабочей кнопки Back в сообщении валидации.

Эти проверки не являются ручным Telegram click-through, новым Hermes-анализом,
production/SSH проверкой или доказательством юридического качества. Network I/O
синтетический; PostgreSQL/RLS/MinIO проверяются отдельно. ConversationHandler
timeout в этих harness не запускается: PTB сообщает об этом warning.
Дополнительный V1 same-state old-card сценарий воспроизвёл изменение другого
V1-черновика; контроль текущей кнопки проходил. После расширения guard на
legacy production `_ask`/resume текущая кнопка работает, старая не меняет
новую карточку; исходные V1 поля и schema сохраняются.
Все возможные виды media и сочетания пользовательских действий здесь не доказаны.
Отдельный bounded timing RED показал отсутствие ACK при заблокированном Core
read. После исправления ACK виден до завершения read, protected output отсутствует
во время блокировки, underlying handler не отправляет второй ACK, следующий
update получает собственный ACK и область вызова освобождается.
Независимая дополнительная проверка обнаружила stale MATERIALS overwrite;
runtime RED воспроизвёл изменения до и во время upload и download/parsing
после отзыва доступа. Проверки исправления включают также изменение после
post-receipt GET: optimistic конфликт сохраняет новые факты.
