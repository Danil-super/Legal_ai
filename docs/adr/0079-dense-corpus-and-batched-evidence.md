# ADR 0079: плотная нормативная база и один снимок проверки на план поиска

## Контекст и дата

2026-10-12. Исправление ADR 0078 прошло тесты, но рабочая библиотека ещё превышала
20 секунд. В одном реальном документе 8960 фрагментов, в другом 4,76 млн символов.
Проверка всех 54 утверждённых версий заняла 22,72 секунды. Поэтому выпуск 0078
не был объявлен завершением исправления.

## Решение

- Миграция c2e8a1b4d630 сначала ищет точное UTF8-совпадение в окне около прошлого
  фрагмента. При промахе выполняется прежний поиск суффикса и всего документа.
  Никакие условия approval, hash, source, роли и дат не удаляются. Расчёт длины
  окна использует bigint и ограничен длиной полного текста. Downgrade возвращает
  прежнее тело helper, не меняя данные.
- Python preflight аналогично использует find со старта предыдущего совпадения,
  затем полный поиск. Перестановки, повторы и перекрытия не запрещаются.
- search_many добавляет ограниченный локальный пакет: максимум 20 запросов,
  прежние ограничения строки и числа результатов, отдельный упорядоченный список
  для каждого запроса. production_legal_fragments и дата проверяются в одном
  MATERIALIZED снимке SQL. Это не кеш между запросами. Ранжирование, round-robin,
  исключение pending и отсутствие фрагмента сохраняются.
- При настроенном semantic provider используется прежний search на каждый запрос
  с исходным semantic флагом: privacy redaction и RRF не меняются. Нет нового
  провайдера, source, risk policy или права доступа. HTTP-контракты прежние.
- Чтение библиотеки выполняется в ограниченной фоновой очереди gateway, а не
  в последовательном обработчике Telegram. Повторное нажатие не создаёт дубль;
  остановка приложения отменяет ожидание. Авторизация остаётся в прежнем API.

## Проверка

Добавлен синтетический вариант 1,93 МБ / 9000 фрагментов. До дополнительного
исправления approval 3,23 с; после SQL и Python оптимизации 1,60–1,67 с.
Бюджет 2 секунды не ослаблялся. Проверяются Unicode, перекрытия, обратный порядок,
отсутствующий текст и промежуток свыше окна. Отдельный PG-тест сравнивает точные
списки и порядок результатов search_many с одиночными search, включая pending
и истёкшие версии. Невозможность вернуть данные после отзыва роли проверяет
прежний DB guard, он не заменяется метаданными approval_state.

На сервере временные функции, откатившиеся вместе с тестовой транзакцией,
проверили тот же набор 54 версий: все проверки сохранились; время 22,72 → 17,13 с.
Это ещё не проверка итогового API или юридического качества ответов. Выпуск
требует зелёного CI, новой закрытой копии БД и повторной проверки реального API.

## Рабочий HTTP-лимит

После выпуска c2 библиотечный SQL измерен на сервере: 18,10 с, HTTP — 19,84 с.
20-секундный клиентский лимит не оставлял запаса и продолжал давать тайм-ауты.
Только GET /v1/legal/library получает read/connect/network timeout 60 с; общая
фоновая задача ограничена 90 с, чтобы вместить дополнительный проверяемый запрос
ссылки на справочники. Прочие запросы остаются с прежним default 20 с; approval
сохраняет свой отдельный лимит. Ограничение очереди, shutdown cancellation и
повторный auth в API сохраняются. Нет ослабления approval/retrieval guard.

План из 9 запросов на рабочей базе дал 20 фрагментов 11 версий за 48,38 с.
В пакетном снимке lower/to_tsvector теперь вычисляются один раз на фрагмент,
а не заново для каждого запроса и каждого этапа ранжирования. PG-тест сохраняет
точное равенство результатов с одиночными запросами. Read-only проверка нового
SQL на той же рабочей базе: 9 запросов, 44 кандидата за 27,08 с.
Runtime orchestrator получает HTTP-лимит Legal Core 60 с для контекста/повторной
валидации submission; общий бюджет анализа 115 с, worker и lease не увеличены,
тайм-ауты моделей 30/50 с не меняются. Это устраняет преждевременную отмену
20-секундным клиентом, но не обещает успех, если общий бюджет исчерпан.
