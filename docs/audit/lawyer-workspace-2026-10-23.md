# Readable lawyer workspace and owner-mediated assignment

## Scope and state

Implementation and local verification complete. Production release and real-case
assignment have not been performed by this change. Release requires owner approval
and successful exact-head GitHub checks. ADR 0096 records the approved permission.

The reported case was already claimed by the owner. A lawyer's inability to steal
that claim was expected authorization, not a failed claim request. The readable
card work had remained local, so production still displayed raw fields.

## User-visible behavior

- The card presents a situation summary, services, dates, clinic actions, health
  signals and factual clarifications with readable labels. It handles legacy facts
  as well as guided-v2 and preserves the full text in the complete card.
- The complete saved report uses the existing report presenter instead of raw JSON.
- An assigned owner is identified as the clinic owner, not as another lawyer.
- An owner opens the case, selects **Передать юристу**, selects a same-clinic active
  lawyer and confirms. Opening the selector does not transfer the case.
- The assignee sees the case in the queue, can ask questions in the existing case
  discussion and save a conclusion using **Завершить обращение**. Other lawyers
  cannot take over the case or resolve it. The history is not rewritten.
- Expired, cancelled, unknown and stale selection controls cannot authorize changes.

This change does not add an AI action plan for HIGH/CRITICAL or change Hermes,
risk policy, legal approvals, clinical facts, attachments or patient delivery.

## Verified defects corrected before release

1. `closed_at` denotes intake confirmation and starts retention; it must not block
   later assignment. A real facts → intake-finalization → assignment regression
   verifies this, rather than relying only on hand-seeded cases.
2. A recipient-lock wait could allow assignment after case closure. Assignment now
   locks Case before escalation and recipient, consistent with retention ordering.
   Concurrent closure serializes before or after assignment; it cannot be silently
   ignored. Tests observe actual PostgreSQL blocking relationships.
3. PostgreSQL `now()` represents transaction start. Target access might expire while
   assignment waits. Locked entitlement and retention dates are rechecked against
   current UTC time before writing the workflow event.

## Dependency review

The initial audit found advisories in two existing packages. Only certifi
2026.7.22 → 2026.10.19 and Pillow 12.3.0 → 13.0.0 were updated; other version pins
remain unchanged. The lock was regenerated by the project's pip-compile process.

Pillow 13 is a major update, not assumed to be a transparent patch. Reviewed its
[official compatibility/removal notes](https://pillow.readthedocs.io/en/stable/releasenotes/13.0.0.html),
including Python >=3.11 and removed image APIs. There are no first-party PIL
imports; the full PDF/ReportLab tests and rebuilt images use the updated dependency.
Certifi's version is the [upstream release](https://github.com/certifi/python-certifi/releases/tag/2026.10.19).

## Deployment and rollback

Before release, obtain owner approval, require GitHub CI and a normal server backup.
Use the existing pinned-commit deployment workflow; migration e21b7c4d8a90 adds a
nullable assignment target, same-clinic FK and event-shape check without rewriting
events, weakening RLS or changing role grants. Verify revision, migration head,
health checks, owner selector and lawyer actions after deployment. Do not silently
transfer the real case: the owner explicitly confirms in Telegram.

After the first ASSIGNED event, rollback must retain assignment-compatible Core
readers. Do not redeploy pre-assignment readers that confuse actor with recipient,
erase workflow history or restore an old database over subsequent clinic work.
The migration refuses destructive downgrade when ASSIGNED history exists; use a
forward fix if necessary. Legal approvals and risk policies are unchanged.
